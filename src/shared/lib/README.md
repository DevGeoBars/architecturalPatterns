# Shared Lib

`shared/lib` содержит небольшие внутренние библиотеки общего назначения, которые служат фундаментом приложения и не знают о его бизнес-предметной области.

`lib` — это не папка только для функций и не склад произвольных `utils` или `helpers`. Формат файла не определяет его размещение: библиотека может содержать функции, типы, классы, React-хуки и при необходимости JSX. Определяющим является назначение кода и его принадлежность к одной ограниченной технической задаче.

## Что можно добавлять

Код можно поместить в `shared/lib`, если он:

- не содержит бизнес-логики ServiceDesk;
- не знает о сущностях, фичах, виджетах, страницах и слое `app`;
- решает одну небольшую, чётко сформулированную техническую задачу;
- потенциально применим в разных частях приложения;
- имеет понятную границу ответственности и минимальный публичный API.

Текущие примеры:

- `classNames` — формирование строки CSS-классов;
- `lazy-loading` — вспомогательный механизм ленивой загрузки страниц;
- `storage` — типизированная работа с браузерным хранилищем;
- `typeGuards` — общие проверки и сужение типов;
- `urlJoin` — безопасная сборка URL.

Если библиотека состоит из нескольких файлов, она размещается в отдельной папке и предоставляет явный публичный API через `index.ts`. Экспортировать следует только то, что требуется потребителям. Для библиотеки с неочевидными правилами или расширяемой областью ответственности следует добавить собственный `README.md`.

## Что не нужно добавлять

В `shared/lib` не следует помещать:

- бизнес-типы, правила и преобразования, относящиеся к конкретной сущности;
- код конкретной фичи, виджета или страницы;
- React-компоненты, назначение которых — отображать интерфейс: им место в соответствующем сегменте `ui`;
- API-клиенты и взаимодействие с backend: им место в `shared/api` либо в `api` соответствующего бизнес-слайса;
- глобальную конфигурацию приложения: ей место в `shared/config` или `app` в зависимости от ответственности;
- файлы, объединённые только по технической форме, например общие папки `hooks`, `types`, `components`, `utils` или `helpers`;
- код «на будущее», у которого пока нет реального потребителя и ясной ответственности.

Нельзя добавлять новую несвязанную функциональность в существующую библиотеку только потому, что она является общей. Для каждой самостоятельной задачи нужна собственная ограниченная библиотека.

## Когда нужен отдельный сегмент Shared

Если технический механизм является самостоятельной инфраструктурной подсистемой, имеет собственный устойчивый публичный контракт и объединяет несколько видов кода, отдельный сегмент может точнее выражать его назначение, чем путь через `lib`.

Например, React-интеграция с DI-контейнером включает Context, Provider и хуки. Поэтому она находится в `shared/di`, а не в `shared/lib/di`:

```text
shared/di — общий механизм работы с DI в React
app/di    — создание контейнера и регистрация сервисов ServiceDesk
```

Наличие JSX или Provider само по себе не требует отдельного сегмента. Решение принимается по ответственности: `shared/lib` подходит для сфокусированной внутренней библиотеки, а отдельный сегмент — когда его имя заметно точнее описывает самостоятельную инфраструктурную область проекта.
